# Workspace usability review — 9 September 2026

The current task was to simplify the existing running frontend while preserving the backend and specialist workflows. This is not a claim of production completion against the entire v3 plan.

## Everyday workflow

- Five primary destinations: Dashboard, Upload files, Review differences, Agent history, Finish month.
- Dashboard explains the agent's purpose and the human approval boundary, then shows a next step based on this month's actual files, held imports, unmatched records, recommendations and certification state.
- Three summary cards show matched entries, open differences and ready recommendations. Priority differences and bank/accounting source readiness stay visible.
- Upload has two steps, file type detection and collapsed optional column mappings. Validation errors retain their existing held-file review and rejection workflow.
- `POST /api/check` combines source-readiness validation, existing matching and recommendation preparation. Repeating a completed check does not recreate prepared recommendations or matches. Role and month-lock checks still apply.
- Review uses plain statuses, references and explicit next-action buttons. Analysts can inspect evidence; reviewer approval remains required.
- Existing specialist pages remain under More tools. Desktop and mobile styles are in `frontend/src/experience.css`; the dashboard is its own `Dashboard.tsx` component.

## Findings addressed

- Workspace, pilot and evidence-export reads now require a signed session. Internal user credential records are excluded from workspace responses and export payloads; export checksums describe the sanitized payload.
- Session expiry and logout clear visible workspace/dialog state and return to Dashboard for the next login.
- Agent history/help no longer incorrectly claim there is no model usage or that already-integrated bank formats are missing.
- Example-data notice no longer labels user-uploaded records synthetic.
- Monetary display handles negative fractional values and large decimals. Ageing totals use exact decimal arithmetic; monthly summaries separate currencies. Manual-match preview rejects mixed currencies and uses exact decimal arithmetic for its tolerance check.
- Browser tests start separate local servers and a fresh SQLite database, with LLM API keys disabled. They do not seed or mutate the user's running workspace.

## Review scope and remaining boundaries

Reviewed repository structure, current frontend screens and interactions, workbench API/auth/storage/matching/review paths, existing core module interfaces, tests and implementation-status documentation. The test suite provides regression coverage; this is not an independent financial or security audit of every source line.

The existing local SQLite/demo-account boundary remains. Production identity, tenancy, external posting and other roadmap gaps remain tracked in `IMPLEMENTATION_STATUS.md`. Manual matching deliberately allows human cross-account overrides in the existing implementation/tests; that business policy was preserved. Numeric journal entry validation continues to be enforced by the backend Decimal model.
